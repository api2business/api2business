# 额度监控

- 额度监控的唯一业务入口是 Api2Business 的 `/quota-monitor` 页面和对应的
  `/api/upstreams/*` 接口；数据库 authority 是 NC01 本地 Sub2API 专用库。
- Web、worker 和 CLI 只通过 Api2Business 排队读取 broker 访问数据库，不直连旧运行面或从
  Sub2API 管理 API 另取一套状态。

## 数据口径

- 钱包余额来自现有上游资产汇总的 `walletDistribution` 与 `totalRemainingCny`，单位统一为人民币。
- 余额钱包身份由 owning YAML 的 `sub2api.newApiCredentials[].walletKey` 定义；同一钱包可以
  通过多个 API host、`/v1` 别名或多个平台账号访问。未配置 `walletKey` 时才回退到去除
  末尾斜杠并归一化 `/v1` 的上游地址。页面、账号缓存、V2 作用域和趋势采样都使用这个
  钱包身份，不能在页面另造 URL 映射。
- 充值账本仍按充值命令传入的规范化 `base_url` 记账；它与余额读取的 `walletKey` 是两个
  明确边界，不能因为同一余额而重复记充值，也不能把账号成本或质量样本合并成钱包级样本。
- 24 小时真实供应商成本统一从同一条排队数据库查询读取 `usage_logs.actual_cost`，
  时间窗为 `created_at >= now() - interval '24 hours'`；失败或缺失记录不补假值。
  该字段可能包含逐条下游售卖倍率；先按每条记录的
  `actual_cost / rate_multiplier` 折回，再乘同一额度缓存中实时读取的有效倍率，
  由共享 `providerActualCostUsd` 函数完成；任一实际记录缺售卖倍率或实时倍率时留空。
- 结果再按钱包资产汇总中的 `remainingCny / remainingUsd` 换算为人民币，
  不读取 `account_stats_cost` 或标准 `total_cost` 作为实际支出，也不把缺失值回退成其他成本字段。
- 一个账号挂多个分组时，按实际分组汇总且不能因分组连接重复计算；一个钱包的总消耗等于其账号消耗之和。
- 现场对账金额只能作为该时刻的核对证据，不能硬编码、缩放或写入通用规则。

## 经验与反模式

### 共享钱包别名与跨作用域读取

- 正确做法：在 owning YAML 为同一供应商钱包的每个可读 host 声明同一个 `walletKey`，
  Secret 只复用 `sourceRef` 和 `sourceKey`，不把用户名、密码或 Token 写进配置。
- 正确做法：凭据查找使用归一化后的钱包地址，因此 `https://host` 与
  `https://host/v1` 命中同一份只读登录凭据；结果再写入统一的上游额度缓存。
- 正确做法：V2 读取完整额度缓存后按 `walletKey` 选择最新成功的有限 USD 余额，投影到
  Codex、Claude、Grok 等作用域的同钱包账号；账号仍保留自己的用量、成本、状态和质量字段。
- 正确做法：读取历史 V2 快照时也重新投影 `accountBalanceCny`；旧快照缺少该字段不等于
  余额未知，必须从额度监控缓存的成功结果补齐后再交给页面和调度器。
- 正确做法：优先级计划使用与页面相同的共享钱包回退；账号自身没有成功探测记录时，使用
  同钱包别名的最新成功结果，避免页面有余额而调度器仍按未知余额排序。
- 共享钱包的成功有限余额按事实排序：最新成功的正数余额优先于同轮或后续账号返回的零值；
  成功返回的零才是有效耗尽状态，失败、限流、`null` 或“不限额”不能覆盖已有的有限余额。
  同一 `walletKey` 每轮只读取一次钱包证据，其他账号和作用域只复用这份缓存，不追加供应商请求。
- 正确做法：旧额度接口返回账号行时也做同一钱包投影，保证旧页面与 V2 不出现短时间的
  余额分叉；额度接口不得再套用通用 API 响应缓存。
- 反模式：只按账号的 `base_url` 展示余额。一个钱包经由多个 host 读取时，会把同一余额
  错误显示成多个不同的钱包。
- 反模式：只在一个作用域或一个账号查询额度，再把其他作用域标成“不限额”、零或未知；
  同钱包必须复用最近成功的有限余额证据。
- 反模式：只给新鲜快照写入 `accountBalanceCny`，遇到旧快照就直接显示未知；快照 schema
  升级应在读取边界完成兼容投影，不能要求用户先手动重建全部缓存。
- 反模式：页面和优先级计划各自实现一套钱包匹配；这会产生“页面有余额、调度器余额未知”
  的分叉，钱包归一化和别名回退必须共享同一配置来源。
- 反模式：请求失败时覆盖 `last_success_result` 或趋势余额。失败只更新失败状态和查询
  时间；没有成功证据时保持未知，不能伪造零值。
- 反模式：为了刷新 V2 余额另起供应商请求。V2 只读额度监控缓存，避免首屏慢、跨作用域
  读数不一致和供应商重复请求。

- 正确做法：用数据库 `created_at >= now() - interval '24 hours'` 固定滚动窗口，逐条除以
  `rate_multiplier`，再乘额度缓存中同一账号的实时有效倍率。
- 正确做法：所有账号先完成供应商美元成本计算，再按共享钱包的人民币换算率合并；钱包
  汇总表只显示一行，账号表仍为每个账号显示同一钱包余额。
- 正确做法：销售倍率、实时有效倍率或钱包换算证据缺失时留空，并在状态中保留可解释的缺失原因。
- 反模式：直接汇总 `actual_cost`；Claude 等账号会把下游销售倍率重复计入，结果按倍率成倍偏高。
- 反模式：把上游 `usage.total` 当作 24 小时值；它通常是累计值，不能替代数据库滚动窗口。
- 反模式：把 `usage.today` 当作滚动 24 小时值；它是自然日窗口，跨日时会漏算。
- 反模式：把 `account_stats_cost`、`total_cost` 或账号名称后缀直接当供应商实际支出；它们分别属于账号统计、标准成本和配置提示。
- 反模式：给额度监控接口叠加通用 HTTP 快照缓存；页面会继续显示旧对账结果，必须沿用额度缓存刷新链路。

## 可用额度

- 状态必须从额度监控 SQL 返回的数据库字段读取：`status`、`schedulable`、
  `temp_unschedulable_until`、`rate_limit_reset_at`、`overload_until`、`expires_at` 和
  `auto_pause_on_expired`。
- 账号只有同时满足以下条件才贡献绿色可用额度：`status=active`、`schedulable=true`，且临时不可调度、限流、过载和过期暂停时间均未生效。
- 同钱包多个账号不能因为其中一个可用就把整个钱包标绿；按钱包内各分组账号的可用占比折算可用额度，其余为不可用额度。
- 圆盘分母是该分组的剩余额度，绿色比例是可用剩余额度除以分母，不使用消费金额计算。

## 缓存与刷新

- 普通页面打开只读取已有缓存；缓存未建立时显示明确空态，不隐式发起第二套拉取。
- 刷新必须沿用同一缓存键：先提交额度刷新作业，使用 `/api/upstreams/jobs/<id>` 轮询原作业到终态，再以 `x-api2business-refresh: 1` 读取并写回额度监控缓存，最后读取刚写入的缓存。
- 不得用 `/api/admin/workflows/<id>` 轮询上游额度刷新作业；该入口要求管理 API 凭据，会把正常刷新误判为登录失效。
- 刷新期间保留已有前端数据，只显示加载动画；刷新失败显示失败原因并恢复按钮，不清空旧数据。
- 缓存刷新成功的判定必须同时核对 `x-api2business-cache: refreshed`，随后普通读取命中
  `x-api2business-cache: hit`，不能只看 HTTP 200/202。
- 账号用量读取接口的 `accountIds` 单次上限是 100；前端账号数超过 100 时必须分块读取后合并，不能把上限错误地当成系统总账号数上限。
- 若页面突然停在“正在读取额度缓存”或钱包表格为空，先检查接口是否返回
  `accountIds must contain 1 to 100 stable IDs`；这属于请求分块回归，不是额度缓存丢失。

## 余额趋势采样

- 请求失败不是余额归零：写入趋势采样时沿用同一 `walletKey` 最近成功的数值余额。
  - 保留本次 `probeOk=false` 和原成功来源时间，不能把回退值标记为新查询成功。
  - 成功返回的真实零余额必须更新为零；首次失败且无成功证据时保持未知。
  - 读取既有失败历史点时按时间顺序沿用此前成功余额，不使用未来值倒填。
  - 原始失败记录保留，不为平滑曲线修改数据库审计事实。
- 余额采样由 owning YAML 的 `operations.upstreamManagement.quotaSampleIntervalSeconds` 控制，当前值为
  `600`，即每 10 分钟写入一次持久化额度样本；现场修改配置后必须通过项目 CLI 重启运行面。
- 同一 `walletKey` 在一个采样轮次只读取一次账号钱包余额证据；多个 API host 和账号复用该轮次结果，账号自己的 token 用量仍按账号读取。
  New API 登录态在进程内跨轮次复用，并在 Access Token 到期后使用 Refresh Cookie 续期，不能每轮重新签发登录 Session。
- `429 AUTH_SESSION_ISSUANCE_LIMIT` 表示上游拒绝新 Session 签发，不是余额为零；保持上一份成功钱包余额，等待既有登录态续期或上游限流窗口恢复。限流失败在进程内冷却 30 分钟，同一钱包不会在每个采样轮次重复申请登录。
- 曲线读取 `/api/upstreams/quota-summary` 返回的同一缓存摘要，不另起额度拉取或缓存；前端复用
  `historyChartMarkup` 绘制 Codex 混池、不降智、Claude、Claude Kiro、Grok 五条人民币余额曲线，共用采样时间轴。
- 曲线点来自已落库的额度样本，并按当前数据库分组映射归入五组；Claude Kiro 先于通用 Claude
  识别，无可用历史样本时保持空态，不以当前余额伪造历史点。
- 同一 `walletKey` 同时承载多个平台时，余额是共享钱包事实；平台曲线可能重复显示同一钱包，
  这不等于账号被错误加入另一平台。扩展平台实时成本前，必须先完成平台归属核对，
  再采用独立钱包或有证据的分摊规则，不能把共享余额直接当成各平台独立资产相加。
- 页面“刷新缓存视图”只读取已有缓存，不触发采样；“手动强制采样”才提交一次
  `upstream.quota.sample` 作业，终态成功后再读取同一缓存，因此手动点和定时点走同一落库与曲线链路。
- 自动刷新默认 30 秒，可切换为 60 秒或 5 分钟；刷新或采样进行中分别锁定两个操作按钮并显示旋转动画，避免重复提交。

## 产出曲线的零值与缺失值

- 产出累计值和余额探测是两条独立证据链；余额请求失败不能擦除同一轮仍然有效的累计产出。
- 相邻采样的累计产出相同，且两个采样点都是真实计数器值时，区间产出按 `0` 计算，曲线显示
  `¥0.000`，并参与滚动速率、评分和成本计算。
- 采样没有任何累计产出证据时才显示未知；首次只读到非零累计值时不把历史累计值倒算成当前区间产出，
  直到下一个可比较的计数器点到达。
- 余额探测失败、成本费率未知与真实零产出分别保留自己的状态，不把任一状态强行转换成零、最低优先级
  或“无数据”。实现与回归测试唯一见 [`src/upstream-quota-monitor.ts`](../../src/upstream-quota-monitor.ts)
  及其测试；本节只维护业务口径。

## 前端缓存与自适应图表

- 页面、主模块和共享图表模块必须一起递增资源版本；只更新主页面而保留旧的模块查询串，会让浏览器继续执行旧的绘图或缓存逻辑。
- 曲线 SVG 的 viewBox、绘图区和 CSS 高度必须来自同一个响应式尺寸；不得让固定高度或 `!important` 规则覆盖脚本计算的画框高度。
- 首次渲染使用视口高度作为布局基准，随后通过 `ResizeObserver` 按外框变化重绘；桌面和移动端不得维护两套坐标算法。
- 验收截图必须人工查看实际绘图区是否填满画框；截图文件存在、页面可打开或 HTTP 成功不能替代可见结果核对。

## 复核与验收

- 先核对实时资产总额、钱包合并、账号消耗分组和状态计数，再查看截图；截图只能证明页面可见结果，不能替代数据对账。
- 刷新失败、缓存 miss、401/404 或空结果先核对运行面、语义来源、认证方式和缓存键，再判断产品业务是否失败。
- 只有页面显示五组圆盘、可用/不可用额度、账号级表格和筛选排序分页，并且刷新链路完成终态核对后，才允许按验收邮件规范交付截图。
- 详细 CLI 生命周期和通用缓存规则见 [Api2Business 技能](../SKILL.md)；上游创建、充值和调度细节见
  [上游与调度](upstream-scheduling.md)。
