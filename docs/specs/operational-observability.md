# 运维观测与固定窗口对账规格

## 独立系统与同一窗口

- Sub2API 的用户请求与 Api2Business 的管理接口分别计算 SLI/SLO。
  - 目标值由 owning YAML 的 `observability` 声明，只用于展示，不自动改变调度或账号。
- 默认窗口为结束时刻之前两小时，显式起止时间使用同一半开区间 `[start,end)`。
  - 请求数、失败数、TTFT 和成本使用同一窗口，不使用最近 N 条样本替代。
  - 内部探活按用户、API key 和分组标识排除，保留排除数量。
  - 不提供服务的语音请求不进入成功率、失败率和 TTFT，保留 `excludedAudioRecords`。
    - 历史实际费用继续纳入成本，不与质量样本混为一谈。
    - 判定与配置唯一见
      [不提供语音服务](../../skills/api2business/references/upstream-scheduling.md#不提供语音服务)。
  - 同一 request ID 去重；窗口内成功记录优先于切号过程错误。
  - 缺少 request ID 的记录单列，不能混进唯一请求分母。
- Sub2API 成功率为成功请求数除以有终态的唯一请求数。
  - 当前目标为严格大于 95%；等于 95% 不达标，比较使用未舍入值。
  - 报告保存比较符 `gt`；TTFT 和管理 API 继续保存各自的 `lte` / `gte` 语义。
  - 缺少请求 ID 或没有有效样本时保持覆盖不足，不能因降低目标而判为达标。
  - TTFT 来自同窗成功流式请求，披露有效及缺失样本数。
  - 错误分组使用阶段、状态码与结构化类型；unknown 保留数量和可下钻请求 ID。
  - API 不返回原始错误正文、用户身份或凭据。
- Api2Business 可用率按完成的管理 API 请求中非 5xx 比例计算。
  - 排除探活、登录、内部 worker 和观测自身请求。
  - 记录请求完成时间、路径模板、状态码、耗时及运行实例身份。
  - 服务端观测不冒充公网边缘可用率；公网检查单独保留每次状态、耗时和错误。
  - 新启用采集的历史窗口明确显示覆盖不足，不倒填历史或将无样本判为达标。

## broker 与运行身份

- broker 状态直接读取执行器，不经过通用响应缓存。
- 状态包含观测时间、实例身份、启动时间、运行时长、最近完成与最近错误时间。
- 成功后仍保留最近失败的时间及脱敏原因，计数与进程实例绑定。
- 服务重启前后的统计不得拼接为同一累计窗口。
- API HTTP 空闲超时由 owning YAML 的 `runtime.httpIdleTimeoutSeconds` 声明。
  - 覆盖正常的排队与查询时间，不能让运行时默认断连伪装成网关故障。

## 钱包与实际成本

- 成本完整性只对当前上游管理范围内的 API-key 账号判定。
  - OAuth、订阅和其他非 API-key 账号不属于上游管理对象，使用
    `accountingStatus=not_applicable` 表示不需对账。
  - 非 API-key 记录保留在原始记录总数与 `outOfScopeRecords` 中，不进入
    `missingRecords` 和覆盖率分母；不得把它们报告为数据缺失。

- 钱包身份、余额来源和币种换算复用
  [额度监控](../../skills/api2business/references/quota-monitoring.md)。
- 同一钱包只计一次余额，账号和平台只保留关联关系。
  - 共享来源、单轮读取和冲突修复以
    [额度监控](../../skills/api2business/references/quota-monitoring.md#共享钱包别名与跨作用域读取)
    为唯一权威；成本报告和定时巡检复用同一证据。
  - 显示最近尝试、最近成功、成功来源账号及新鲜度。
  - 首次缺失、沿用旧成功、无限额和真实零分别呈现。
- 实际成本逐条使用 `actual_cost / rate_multiplier`，再按有证据的供应商倍率换算。
  - 币种换算使用 owning 估值配置，不能用余额差替代成本。
  - 优先复用已持久化的额度采样倍率，逐条匹配不晚于请求时间的最近证据。
  - 手填倍率不冒充真实对账证据；历史证据缺失时保持未知。
  - 部分已知成本与完整成本分开，披露有效记录数、总记录数和缺失原因。
  - 成本覆盖不足时不输出完整成本或续航保证，但必须保留已知部分供风险判断。
  - CLI/API 提供独立的逐日成本入口，默认取过去七天，按钱包汇总余额与关联账号。
    - 同时给出结束时刻前滚动 24 小时成本，不能用今日部分窗口替代近期趋势。
  - 历史缺失不作为充值建议的门槛。
    - 未来24小时预算取实际覆盖日均、完整日峰值与精确最近24小时消费的最大值，再加25%估算余量。
    - 显式区分实测成本、估算预算和缺失记录。
  - 余额未知或陈旧时不能推导“无需充值”；给出临时备付建议和立即核实的动作。
    - 共享钱包去重，不同上游和平台的备选分别评估，建议不执行充值。
    - 发现陈旧余额必须沿 Api2Business 原采样链路排障并修复，核对作业终态与余额成功来源时间。
    - 采样受理、快照生成时间更新或保留旧值不能证明余额刷新成功。
  - 充值报告分为“强烈建议充值表”和“一般储备充值表”。
    - 新鲜可靠余额存在未来 24 小时缺口且影响当前主力供给时，列入强烈建议。
    - 有明确备选资金需求或尚待核实的临时备付，列入一般储备并说明不确定性。
    - 建议充值为零的钱包不进入两张表；同一钱包最多出现一次，无候选时明确写无。
    - 两表同时列出滚动 24 小时实际消耗、预计 24 小时消费和建议充值。
    - 实际消耗复用 `recent24Hours`；部分已知成本标明覆盖，未知不填零，不以预算冒充实测。
- 冻结窗口的报告持久保存其采集时间、来源与结果，后续读取原报告不重新套用当前倍率。
  - 目标调整后生成新报告；旧报告保留原目标、比较符及结论。
  - 页面使用报告中的比较符；早期未存比较符的成功率报告使用原有包含边界的语义。

## 巡检邮件呈现

- 日常邮件分为“两系统状态”“风险与已处理事项”“充值建议”三节。
  - 各节用表格承载可比较的事实，表外用一至三句正文说明结论、原因和后续动作。
  - 表格使用 Markdown 表头与分隔行，前后保留空行；同一事项不在正文重复抄表。
  - 单元格只放短句、数值及必要限定；复杂过程移到表外或证据记录。
  - 不为压缩总字数省略覆盖缺口，也不把长段落全部塞入单元格。
- “两系统状态”使用四列：系统、指标、本轮实测、判定。
  - 表前注明北京时间统计窗口及总体结论，区分服务质量与当前供给状态。
  - Sub2API 分行列请求成功率、流式 TTFT P50/P95 和有效／缺失样本。
  - Api2Business 分行列管理 API 非 5xx 比例、接口延迟和数据覆盖。
  - 各系统同时披露请求数；管理 API 延迟不得写成 TTFT，非 5xx 比例不得冒充业务成功率。
  - 按对应指标目标写达标、不达标、证据不足或不适用；无目标的指标只列实测。
- “风险与已处理事项”使用四列：事项／范围、已核实情况、处理与结果、当前状态。
  - 按下游账务、上游模型／账号、公共运行面及余额数据问题拆行，存在才列。
  - 已执行动作与建议动作分清，配置回读成功与业务恢复分清。
  - 未确认根因、未完成验证及外部依赖在表外简述，写清仍需执行的动作。
  - 无事项时写“本轮无新增风险或处置”，不制造空表或虚构处理结果。
- 充值候选、分级、字段与零建议过滤遵循本规格“钱包与实际成本”。
  - 两张充值表继续独立展示，余额新鲜度、成本覆盖和预算假设放在表外。
- 发送前核对实际 Markdown 邮件正文符合上述结构，不能只修改聊天摘要。
  - 详细请求链、计算明细和操作记录留在 TaskTree，邮件保留可访问的证据引用。

## 验收

- 用重复请求、切号后成功、探活、缺少 ID、缺少倍率和共享钱包夹具验证分子分母。
- 从正式入口连续读取额度与充值候选，保留每轮时间、错误与运行实例变化。
- Web 与 CLI 读取相同报告，展示两套独立 SLO、窗口、覆盖不足及未知原因。
- 原始历史错误不因一次成功或一次部署被改写为持续恢复。
