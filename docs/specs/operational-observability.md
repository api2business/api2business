# 运维观测与固定窗口对账规格

## 独立系统与同一窗口

- Sub2API 的用户请求与 Api2Business 的管理接口分别计算 SLI/SLO。
  - 目标值由 owning YAML 的 `observability` 声明，只用于展示，不自动改变调度或账号。
- 默认窗口为结束时刻之前两小时，显式起止时间使用同一半开区间 `[start,end)`。
  - 请求数、失败数、TTFT 和成本使用同一窗口，不使用最近 N 条样本替代。
  - 内部探活按用户、API key 和分组标识排除，保留排除数量。
  - 不提供服务的语音请求不进入成功率、失败率和 TTFT，保留 `excludedAudioRecords`。
    - 历史实际费用继续纳入成本，不与质量样本混为一谈。
    - 判定与配置唯一见
      [不提供语音服务](../../skills/api2business/references/upstream-scheduling.md#不提供语音服务)。
  - 同一 request ID 去重；窗口内成功记录优先于切号过程错误。
  - 缺少 request ID 的记录单列，不能混进唯一请求分母。
- Sub2API 成功率为成功请求数除以有终态的唯一请求数。
  - 已明确归属下游用户的余额或 Key 额度限制不进入服务质量分母。
  - 排除数量保留为 `excludedBusinessLimitRecords`，身份与影响保留在账务分解中。
  - 没有用户归属或不满足账务限制证据的失败继续计入，不泛化排除所有业务错误。
  - 当前目标为严格大于 95%；等于 95% 不达标，比较使用未舍入值。
  - 报告保存比较符 `gt`；TTFT 和管理 API 继续保存各自的 `lte` / `gte` 语义。
  - 缺少请求 ID 或没有有效样本时保持覆盖不足，不能因降低目标而判为达标。
  - TTFT 来自同窗成功流式请求，披露有效及缺失样本数。
  - 错误分组使用阶段、状态码与结构化类型；unknown 保留数量和可下钻请求 ID。
  - `sourceCoverage` 单列已完成但缺用量的原生警告及未关联请求。
    - 同窗按请求去重，排除已核实探活和语音；精确用量关联后不再算源缺口。
    - 保留模型分解、日志抑制数及有界请求示例，不输出原始日志扩展字段。
    - 未关联、采样抑制或查询失败时保留覆盖不足，不增加成功、失败或延迟样本。
    - 模型未知时不能推定为 Luna；任务过滤仍按已核实模型身份执行。
  - API 不返回原始错误正文、用户身份或凭据。
- Api2Business 可用率按完成的管理 API 请求中非 5xx 比例计算。
  - 排除探活、登录、内部 worker 和观测自身请求。
  - 记录请求完成时间、路径模板、状态码、耗时及运行实例身份。
  - 服务端观测不冒充公网边缘可用率；公网检查单独保留每次状态、耗时和错误。
  - 新启用采集的历史窗口明确显示覆盖不足，不倒填历史或将无样本判为达标。
  - 采集失败按原发生时间限定在同一半开窗口，实例累计数量另行保留。
  - 旧实例没有失败时间时保留 `unlocatedFailedWrites`，不得猜测历史窗口完整。

## 自动运维的模型范围

- Sub2API / Api2Business 自动运维任务的总评分与优化目标排除 Luna。
  - 质量统计的 Luna 排除沿用
    [上游质量统计边界](../../skills/api2business/references/upstream-scheduling.md#稳定性观察与用户报错)。
  - 按请求模型、实际模型与上游模型识别 Luna 及已核实别名，不能排除整个供应商或平台。
  - 账号分与池分沿用既有 Luna 排除，不重写评分公式或修改其他模型目标。
- 任务的整体成功率、失败率和 TTFT 判定先排除 Luna，再在同窗请求上重新聚合。
  - 同时排除其成功、失败和延迟样本，保留纳入数、排除数、有效及缺失样本与来源。
  - TTFT P95 从剩余有效样本重算，不能平均各模型 P95 或只从失败数中减掉 Luna。
  - 通用报告仍含 Luna 时，原始口径与任务过滤口径分开标识；不能沿用未过滤总数下结论。
  - 缺少完整过滤证据时明确未知并补齐，不能把排除后的无样本当成达标。
- Luna 不作为本任务的异常主线、调度优化、事故恢复、供给补齐或外部协助目标。
  - 旧事故重新核对纳入范围；不能因 Luna 仍失败或没有 Luna 成功样本而阻止其余目标验收。
  - 其他模型及公共运行面问题仍持续处理，不因排除 Luna 而忽略公共故障。
- Luna 原始请求、失败与实际费用继续保留，财务成本不因质量排除而消失。
  - 巡检邮件的总评与行动建议使用过滤口径，简述已排除 Luna，不再列其修复待办。

## 修复后的观察与复验

- 修复或改进生效后观察 10 分钟即可复验，不要求覆盖完整两小时窗口。
  - 两小时仍是常规巡检的历史调查窗口，不是修复后的强制等待时长。
  - 已积累的新鲜修复后证据可以复用，不为本轮重新等待 10 分钟。
- 复验使用明确的修复后 10 分钟起止时间，核对正式入口、原异常、受影响范围和自然业务。
  - 同窗计算两系统指标，保留有效、缺失样本和覆盖，不把短窗称为完整历史窗口。
  - 修复前的失败与历史 SLO 如实保留，不因其尚在两小时滚动窗口内而拖延修复验收。
  - 无样本或缺数据不能写成恢复；原异常仍存在时继续处置，不以 10 分钟已到宣告完成。
- 未完成状态、必要审批和结果邮件的边界见下文
  [巡检邮件呈现](#巡检邮件呈现)。

## 服务质量归因

- 先区分公共运行面或网关、具体上游模型或账号、下游用户或 API Key 账务限制。
  - `businessLimitBreakdown` 的用户归属和余额、额度限制证据用于排除账务误报。
  - 未明确归属的失败继续调查，不能泛化排除所有业务错误。
- 全局成功率或 TTFT P95 不能单独确定根因。
  - 同窗读取 `businessLimitBreakdown` 与 `ttftBreakdown`，按模型和上游账号下钻。
  - 探活记录、认证失败、读取失败、空结果与业务失败分别归因。
  - 排除可归因账务限制后，公共或上游失败仍存在、或 SLO 未达标时继续质量调查。
- 模型异常须核对真实 `model_mapping`、模型同步结果和上游余额。
  - 单次失败请求不能证明模型被删除或账号池无可用模型。
- 候选质量与池级低分的调查、调度器维护和整体供给判断见
  [自动巡检低分归因与处置](../../skills/api2business/references/upstream-scheduling.md#自动巡检低分归因与处置)。
  - 邮件与外协判断统一服从下文[巡检处置范围](#巡检处置范围)。

## broker 与运行身份

- broker 状态直接读取执行器，不经过通用响应缓存。
- 状态包含观测时间、实例身份、启动时间、运行时长、最近完成与最近错误时间。
- 成功后仍保留最近失败的时间及脱敏原因，计数与进程实例绑定。
- 服务重启前后的统计不得拼接为同一累计窗口。
- API HTTP 空闲超时由 owning YAML 的 `runtime.httpIdleTimeoutSeconds` 声明。
  - 覆盖正常的排队与查询时间，不能让运行时默认断连伪装成网关故障。

## 钱包与实际成本

- 成本完整性只对当前上游管理范围内的 API-key 账号判定。
  - OAuth、订阅和其他非 API-key 账号不属于上游管理对象，使用
    `accountingStatus=not_applicable`、`reason=non_apikey_not_in_scope` 表示不需对账。
  - 非 API-key 记录保留在原始记录总数与 `outOfScopeRecords` 中，不进入
    `missingRecords` 和覆盖率分母；不得把它们报告为数据缺失。

- 钱包身份、余额来源和币种换算复用
  [额度监控](../../skills/api2business/references/quota-monitoring.md)。
- 同一钱包只计一次余额，账号和平台只保留关联关系。
  - 共享来源、单轮读取和冲突修复以
    [额度监控](../../skills/api2business/references/quota-monitoring.md#共享钱包别名与跨作用域读取)
    为唯一权威；成本报告和定时巡检复用同一证据。
  - 显示最近尝试、最近成功、成功来源账号及新鲜度。
  - 首次缺失、沿用旧成功、无限额和真实零分别呈现。
- 实际成本逐条使用 `actual_cost / rate_multiplier`，再按有证据的供应商倍率换算。
  - 币种换算使用 owning 估值配置，不能用余额差替代成本。
  - 优先复用已持久化的额度采样倍率，逐条匹配不晚于请求时间的最近证据。
  - 手填倍率不冒充真实对账证据；历史证据缺失时保持未知。
  - 部分已知成本与完整成本分开，披露有效记录数、总记录数和缺失原因。
  - 成本覆盖不足时不输出完整成本或续航保证，但必须保留已知部分供风险判断。
  - CLI/API 提供独立的逐日成本入口，默认取过去七天，按钱包汇总余额与关联账号。
    - 同时给出结束时刻前滚动 24 小时成本，不能用今日部分窗口替代近期趋势。
  - 历史缺失不作为充值建议的门槛。
    - 未来24小时预算取实际覆盖日均、完整日峰值与精确最近24小时消费的最大值，再加25%估算余量。
    - 显式区分实测成本、估算预算和缺失记录。
  - 余额未知或陈旧时不能推导“无需充值”；给出临时备付建议和立即核实的动作。
    - 自动巡检先按[巡检处置范围](#巡检处置范围)排除不处置事项。
    - 共享钱包去重，不同上游和平台的备选分别评估，建议不执行充值。
    - 发现陈旧余额必须沿 Api2Business 原采样链路排障并修复，核对作业终态与余额成功来源时间。
    - 采样受理、快照生成时间更新或保留旧值不能证明余额刷新成功。
  - 充值报告分为“强烈建议充值表”和“一般储备充值表”。
    - 新鲜可靠余额存在未来 24 小时缺口且影响当前主力供给时，列入强烈建议。
    - 有明确备选资金需求或尚待核实的临时备付，列入一般储备并说明不确定性。
    - 建议充值为零的钱包不进入两张表；同一钱包最多出现一次，无候选时明确写无。
    - 两表同时列出滚动 24 小时实际消耗、预计 24 小时消费和建议充值。
    - 实际消耗复用 `recent24Hours`；部分已知成本标明覆盖，未知不填零，不以预算冒充实测。
- 冻结窗口的报告持久保存其采集时间、来源与结果，后续读取原报告不重新套用当前倍率。
  - 目标调整后生成新报告；旧报告保留原目标、比较符及结论。
  - 页面使用报告中的比较符；早期未存比较符的成功率报告使用原有包含边界的语义。

## 巡检处置范围

- 能明确归属下游用户或 API Key 的余额欠费只用于排除服务质量误报。
  - 不修复下游账务、不联系欠费用户、不要求充值或外部协助。
  - 详细归因留在原报告或 TaskTree，不列入巡检邮件的问题和协助清单。
- NewAPI 钱包余额无法读取时，保留最近成功值及原时间；没有成功值则保持未知。
  - 供应商登录限制、验证码、余额接口不可用或未提供凭据不属于巡检处置事项。
  - 不反复排障、不索要凭据、不请求外部核验，也不仅因不可查推荐临时备付。
  - Api2Business 自身采样、缓存、投影或冲突缺陷仍按既有规则自行修复。
- 多上游路由由 Api2Business 上游调度器负责，巡检不承担路由职责。
  - 单个上游质量波动交给调度器处理；巡检不逐账号制定路由或手动分流。
  - 巡检负责维护调度器，修复其配置、执行链路和代码缺陷，再验证原调度流程。
  - 不要求用户联系单个供应商或补充该账号的同模型能力。
  - 只有兼容的整体供给不足或公共故障经自行处置仍影响服务，且确需外部动作时，才列协助。
- 上述不处置事项不进入“需外部协助”或紧急标签判断。
  - 仍保留真实失败和成本证据；不能隐藏正常文本失败或把未知余额写成零。

## 巡检邮件呈现

- 本巡检每两小时发送报告，正常、异常、存在未完成事故时均须报告。
  - 这是用户明确授权的定期报告，不以事故闭合、旧审批获批或数据完全齐备为发送前提。
  - 到期用当前已核实数据报告，未知项说明缺口、影响与下一步，不能漏报或伪造健康。
  - 持续处置、定期报告例外和必要审批条件只见
    [未完成任务邮件边界](https://github.com/pikasTech/unidesk/blob/master/.agents/skills/unidesk-email/references/acceptance-mail.md#未完成任务的邮件边界)。
  - 发送报告不等于事故完成；继续调查、修复和复验，跨轮续接原 TaskTree 与事故 Issue。
  - 事故完成仍须正式入口、原异常、受影响范围和自然业务证据达标，不能以 runner 结束替代。
- 通用正文方法只见
  [邮件正文权威](https://github.com/pikasTech/unidesk/blob/master/.agents/skills/unidesk-email/references/body-readability.md)。
  - 本规格只维护业务字段、处置范围及恢复复验口径，不另写通用邮件提示词模板。
- 固定正文为“概述”“发现的问题”“目前处理情况”，最后为“充值建议”。
  - 有外部待办时，在“目前处理情况”之后、“充值建议”之前单列“需外部协助”。
  - 各节均使用同级二级标题；外部待办不得埋在处理情况的要点或子项中。
  - 无外部待办时省略“需外部协助”一节。
  - 除充值表格外，正文使用类似 TaskTree Checkpoint 的简短 Markdown 要点。
  - 每条只写一个结论、问题或动作，必要的影响、结果和协助使用缩进子项。
  - 不使用其他正文表格，不写大段叙述或逐项罗列正常检查过程。
  - “概述”说明北京时间窗口、两系统是否正常及主要影响。
  - “发现的问题”说明关键异常与已知原因，未确认原因明确写未知。
  - “目前处理情况”区分已执行动作、实际收益、已验证结果、尚未完成事项与下一步。
  - “需外部协助”独立说明需要谁、在何时提供什么，以及要解决的问题。
  - 无新增问题或无需用户操作时直接说明，不为凑结构添加细节。
- 定期报告标题使用“【通知】【两小时巡检】Sub2API 与 Api2Business｜北京时间…”。
  - 可加“总体平稳”或“存在异常”，不把尚未解决的事故写成“已处理”。
  - 仅事故处理完成并复验后，事故完成结果才使用“已处理”。
  - 必要审批单独使用“【裁决】”，突出需要批准的动作及收益。
  - 定期报告不替代审批，审批续发的变化条件与旧批准范围见邮件边界。
- 需要外部协助时，必须写清可执行的处理信息。
  - 接下来要做什么，已经做了什么及实际结果，分别说明。
  - 外部协助写明由谁提供什么、用于解决什么问题以及何时需要。
  - 不需用户参与时写明“无需你操作”，不只贴指标或使用“待处理”等空泛结论。
- 邮件只保留支撑结论的少量关键数值，用日常语言解释。
  - 完整 SLO、样本、覆盖缺口、归因及请求链保留在报告或 TaskTree，不在邮件堆叠字段。
  - 证据不足、验证未完成时继续处理，定期报告如实注明；配置回读成功不能写成业务恢复。
  - 事故结果复用上述正文结构，外部待办仍独立成节。
  - 详细时间线与配置差异通过真实 Issue 链接下钻。
- 充值候选、分级、字段与零建议过滤遵循本规格“钱包与实际成本”。
  - 两张充值表继续独立展示，余额新鲜度、成本覆盖和预算假设放在表外。
- 发送前核对实际 Markdown 邮件正文符合上述结构，不能只修改聊天摘要。
  - 详细请求链、计算明细和操作记录留在 TaskTree，邮件保留可访问的证据引用。
  - 自动任务提示词按执行职责归并重复要求，详细规则引用领域权威，不持续追加重复条目。

## 验收

- 用重复请求、切号后成功、探活、缺少 ID、缺少倍率和共享钱包夹具验证分子分母。
- 从正式入口连续读取额度与充值候选，保留每轮时间、错误与运行实例变化。
- Web 与 CLI 读取相同报告，展示两套独立 SLO、窗口、覆盖不足及未知原因。
- 原始历史错误不因一次成功或一次部署被改写为持续恢复。
