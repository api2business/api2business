# Web 登录态与失效复验

## 权威与实现归属

- 登录失效行为和验收会话边界以
  [Runtime 控制规格](../specs/runtime-control.md) 为唯一需求权威。
- V2 的所有读取共用 `static/upstream-scheduling-v2.js` 的请求函数。
  - 初始作用域、快照刷新和探活翻页不能各自遗漏认证失败处理。
- 原生会话签名与过期判定由 `src/web-auth.ts` 维护。
- CLI 参数和正式截图命令只见
  [Api2Business 技能](../../skills/api2business/SKILL.md#验收)。

## 复验与证据

- 正常页面先使用正式登录 API 建立会话，再通过截图 CLI 采集真实业务数据。
- 会话失效取证使用同一截图 CLI 的显式短时效会话和同页连拍。
  - `ttlSeconds`、`fixture` 只披露验收会话元数据。
  - Cookie、密码和签名 Secret 不进入 argv、报告或磁盘。
- 截图回执中的原始失败请求用于定位收到认证失败的请求。
  - 默认使用简洁回执；完整原始事件留在调用方指定的 manifest。
  - 不为查看一次 `401` 读取全量截图输出或解析 stdout dump。
- 失效后的登录页必须与同一轮失效前的业务页面配对检查。
  - 单张登录页不能区分正常导航、初始未登录和打开页面后的会话失效。
- 普通读取失败仍按既有快照容错处理。
  - 会话失效必须进入登录页，不能仅显示“读取失败”并继续轮询。

## 正反经验

- 正向：按每条真实读取路径核对认证处理，并在正文解析前识别 HTTP `401`。
- 正向：用独立短时效会话复验自动刷新，保持部署配置和其他会话不变。
- 反向：只验证首次导航的服务端登录跳转，无法覆盖已打开页面的异步读取。
- 反向：把认证失败归为缓存陈旧或供应商错误，会掩盖用户需要重新登录的事实。
- 反向：临时手写会话签名和浏览器脚本会形成重复入口。
  - 认证与取证复用项目原生函数和正式截图 CLI。
